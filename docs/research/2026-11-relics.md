# Where the game keeps Relics (2026-11-10)

Findings for https://github.com/ANicholasson/raid-bridge/issues/7, part of the Relics spec (https://github.com/ANicholasson/raid-bridge/issues/4).

Relics postdate Raid Toolkit (its last commit is from January 2024), so there was no reference route. Everything above the "Live check" section comes from the installed game's own files: `global-metadata.dat` and `GameAssembly.dll` at IL2CPP metadata v39 and Unity 6000.3.18f1, dated 2026-11-06, parsed with the vendored LibCpp2IL. That part read no game memory and no Account. The "Live check" section then reads the running Game client and the maintainer's Account, and the screen checks there confirm it. The gated installed-files check pins the route to the Account's Relics, a Relic's and a stone's fields, and the static data a Relic's name and bonuses come from. The rest, such as the server's dynamic Relic types, is from the dump only and isn't pinned yet.

## The Account's Relics

The route starts from the Account's root, `_userWrapper`, like every other route:

- `UserWrapper.Relics` is a `Client.Model.Gameplay.Relics.RelicsWrapper`.
- Its `RelicsData` field, declared on the base class `RelicsWrapperReadonly`, is an `UpdatableUserRelicData`. That class derives from `SharedModel.Meta.Relics.UserData.UserRelicData`, which declares the data:
  - `Relics`: `List<Relic>`, every Relic the Account owns;
  - `Stones`: `List<RelicStone>`, every Relic stone the Account owns;
  - `RelicDataByHeroId`: `Dictionary<int, HeroRelicData>`, the Relics each Champion has, by Champion id;
  - bookkeeping the Snapshot doesn't need: `NextRelicId`, `NextStoneId`, `FirstRewardTaken`, `RarityPityCounter` and `PityCounterByGroup`.

The same object is also reachable as `UserGameData.RelicData`. The route above is the one that matches the other readers.

## A Champion's Relics

`SharedModel.Meta.Heroes.Hero` has no Relic field. The link runs the other way, as it does for Artifacts:

- `UserRelicData.RelicDataByHeroId[heroId]` is a `HeroRelicData`;
- its only field, `RelicIds`, is a `List<int>` of Relic ids.

The model keeps a **list** per Champion, but a list doesn't say how many a Champion can wear. That is `StaticRelicData.HeroActivatedRelicsLimit` (an `int`), whose value is in memory, not in the files. When Relics came out (the game's 10.00 release notes), a Champion could wear one. A list fits either way: at most one entry if the limit is one, and no format change if the limit rises. The live check reads the limit. <!-- The limit is unconfirmed: (CodeRabbit, https://github.com/ANicholasson/raid-bridge/pull/16) -->

Two things the files hint at but can't settle, so they need the live check:

- `Relic.IsActivated` is a `Nullable<bool>`. It may mean "worn by a Champion", or something else.
- `RelicActivateRequestDto`, the request the client sends to put a Relic on, has a `HeroId` and two flags: `ReplaceRelicOnHero` and `ActivateRelicForAnotherHero`. The second flag may mean moving a Relic from one Champion to another. It may also mean one Relic can be active on more than one Champion. If two Champions' `RelicIds` hold the same id, the spec's "each Relic appears once" shape doesn't fit.

## A Relic

`SharedModel.Meta.Relics.UserData.Relic`:

| Field | Type | Notes |
| --- | --- | --- |
| `Id` | `int` | The Relic's id on the Account |
| `TypeId` | `int` | Its type in the static data |
| `Rank` | `RelicRank` | `Rank1` = 1 to `Rank6` = 6, no 0 member |
| `Level` | `int` | |
| `IsSeen` | `Nullable<bool>` | Whether the player has looked at it, not needed |
| `IsActivated` | `Nullable<bool>` | See above |
| `Sockets` | `List<RelicStoneSocket>` | Each socket is a `ShapeKindId` (`RelicStoneShapeKindId`) and a `StoneId` (`Nullable<int>`, null when empty) |
| `_type` | `RelicType` | A cache of the static type. The reader uses `TypeId` and the static data instead, as it does for Champions |

A Relic has **no stat values of its own**. It has a type, a rank and a level, and the static data turns those into bonuses (below).

## Relic stones

Relic stones are a part the spec didn't foresee. A Relic has sockets of given shapes, and a stone of a matching shape goes in each one. `SharedModel.Meta.Relics.UserData.RelicStone` has an `Id`, a `TypeId`, `IsSeen`, `IsActivated` and a cached `_type`. A socket names its stone by id, and the stone itself is in `UserRelicData.Stones`.

`RelicStoneType` (static) has an `Id`, a `Name` and a `Description` (`SharedLTextKey`), a `SuperGroup`, a `Rarity` (`ItemRarity`), a `Shape` (`RelicStoneShapeKindId`: `Circle` = 1, `Triangle`, `Square`, `Diamond`, `Pentagon` = 5) and `SkillIds` (`List<int>`). So a stone adds skills, not stats.

## Static data

`ClientStaticData.RelicData`, declared on its base class `SharedModel.Meta.StaticData`, is a `StaticRelicData`. It holds:

- the types:
  - `RelicTypes` and `_relicTypeById` (`Dictionary<int, RelicType>`);
  - `RelicStoneTypes` and `_relicStoneTypeById` (`Dictionary<int, RelicStoneType>`).
- the stat values:
  - `StatValueByLevel`: `Dictionary<StatKindId, List<BonusValue>>`, a value for each stat at each level;
  - `StatBonusOpeningLevels`: `List<int>`, presumably the level at which a Relic's first, second and later stats open.
- the limits and rules:
  - `MaxRelicLevelByRank`: `Dictionary<RelicRank, int>`;
  - `BasicRelicRankByRarity`;
  - `SkillLevelByRelicLevel`: `Dictionary<int, int>`, the level a Relic's skill has at each Relic level;
  - `HeroActivatedRelicsLimit`;
  - `MaxStorageRelicsCount`.
- prices, craft weights and pity settings, which the Snapshot doesn't need.

`RelicType` holds:

- `Id`, and `Name`, `Description` and `Lore` (`SharedLTextKey`);
- `SuperGroup` and `Group`;
- `Rarity` (`ItemRarity`) and `Status`;
- `SkillIds` (`List<int>`) and `SkillIdsByFaction` (`List<RelicFactionSkillBonus>`, each a `FractionId` with its `SkillIds` and a `Description`);
- `StatsBonus`: `List<StatKindId>`, which stats the Relic raises, in order;
- `Sockets`: `List<RelicStoneShapeKindId>`, the shapes of its sockets;
- `SkillLevelDescriptions`.

So a Relic's bonuses are a lookup, not stored values. For each stat in its type's `StatsBonus` whose opening level it has reached, the value is `StatValueByLevel[stat]` at the Relic's level. The live check has to confirm two things about that lookup: how a level indexes the list, and whether each value is flat or a percentage (`BonusValue._isAbsolute`, as for the Great Hall).

A Relic's passive effect is a skill: `RelicType.SkillIds`, plus the `SkillIdsByFaction` entry for the wearer's Faction, at the level `SkillLevelByRelicLevel` gives for the Relic's level. Skill names come from the same skill types the Champion reader already uses.

### Types the server sends

`SharedModel.Meta.Relics.DynamicData.DynamicRelicData` (`Revision`, `RelicTypes`, `LocalizationKeys`; the client's `ClientDynamicRelicData` adds a `Localization` dictionary) arrives with the user's data. It is reached through `UserResponseDto.DynamicRelicData`. So the static `RelicTypes` may not hold every Relic type, and new event Relics may come only from the server. The live check counts how many of the Account's Relic `TypeId`s are missing from `_relicTypeById`. If any are, the reader also needs this route, and a name may come from its `Localization` table.

### Enums

- `RelicRank`: `Rank1` = 1 to `Rank6` = 6.
- `RelicGroup`: `None` = 0, `General`, `Chimera`, `Alice`, `Alliance`, `LiveArena`, `FactionWars`, `DemonInvasion`, `Summer`, `ForgePass`, `Forest`, `Winter`, `Faction` = 12.
- `RelicSuperGroup`: `None` = 0 to `Faction` = 8.
- `RelicStatus`: `None` = 0, `Balance` = 5, `Rebalance` = 10, `PreChecked` = 15, `Checked` = 20.
- `RelicStoneShapeKindId`: `Circle` = 1 to `Pentagon` = 5.

The crafting materials in `resources` (`RelicCraftMaterial_Chimera_Rare` and the rest) match `RelicGroup`'s members.

## In battle

`SharedModel.Battle.Core.Setup.RelicSetup`, on `HeroSlotSetup.RelicSetup`, is the battle's copy of a Champion's Relics. It holds:

- `RelicSkillLevel`, `RelicSkillSetups` and `RelicStoneSkillSetups`;
- `PercentBonus` and `FlatBonus` (`BattleStats`), the Relic's stat bonus as the game itself computed it;
- `RelicInfo` (`RelicLogInfo`).

The Total stats spec can use this as a check (see the stat sources findings).

## Live check (2026-11-10)

A read-only probe read the running Game client on the maintainer's Linux install through the Linux adapter, with each field's offset taken from its runtime class as the reader does. Every route above resolved. The static Relic classes are in `SharedModel.Meta.Relics.StaticData`.

- **How many a Champion wears:** `HeroActivatedRelicsLimit` is 1. It is an instance field of `StaticRelicData`. `MaxStorageRelicsCount` is 300. The `relics` list holds at most one entry today.
- **Shared Relics:** on the Account read, no Relic id appears under two Champions, every listed id is in `Relics`, and every Champion id is one the Account holds. "Each Relic appears once" fits.
- **`IsActivated`:** `true` on the worn Relic and `null` on the unworn one, never `false`. Stones follow the same rule: `true` when socketed, `null` when not. It means "in use", and the reader can't rely on it alone, since "not in use" is `null`, not `false`. The Champion's `RelicIds` and each socket's `StoneId` stay the source.
- **Types the server sends:** none of the Account's Relic or stone type ids is missing from the static tables, which hold 94 Relic types and 120 stone types. The dynamic route isn't needed for now.
- **`StatValueByLevel`:** 7 stats (Health, Attack, Defence, Speed, Resistance, Accuracy and CriticalDamage), each with 19 values for levels 0 to 18. **The list index is the Relic's level.** A value depends only on stat and level, not on rarity or rank. Every stat but CriticalDamage is flat: HP 900 to 6120, ATK and DEF 53 to 398, SPD 3 to 24, RES and ACC 16 to 96. CriticalDamage is a fraction, 0.06 to 0.40.
- **Opening levels:** `StatBonusOpeningLevels` is [0, 9, 15], and every Relic type raises exactly 3 stats. So a Relic's first stat counts from level 0, its second from level 9, and its third from level 15.
- **Rank:** `MaxRelicLevelByRank` is 3, 6, 9, 12, 15 and 18 for `Rank1` to `Rank6`.
- **Skill level:** `SkillLevelByRelicLevel` is {0: 1, 6: 2, 9: 3, 12: 4, 15: 5, 18: 6}. The keys are thresholds: a Relic's skill level is the value of the highest key at or below its level.
- **Sockets:** every socketed stone's shape matches its socket, and no socket names a missing stone.

**Confirmed on the screen (2026-11-10):** a worn Rare Relic at rank 2 and level 3, whose stats are Attack, Health and CriticalDamage, shows ATK +104, which is `StatValueByLevel[Attack][3]`. Its HP and C.DMG show as locked until levels 9 and 15. So the index is the level, and the opening levels apply in the order of the type's `StatsBonus`. An unworn Legendary Relic at rank 3 and level 0, whose stats are Health, Resistance and Speed, shows HP +900, which is `StatValueByLevel[Health][0]`, with RES and SPD locked until levels 9 and 15, and three empty sockets.

## Against the spec's shape

| Spec (https://github.com/ANicholasson/raid-bridge/issues/4) | The game | Fits? |
| --- | --- | --- |
| A worn Relic under its Champion | `RelicDataByHeroId[id].RelicIds`, a list | Yes, as a list, `relics` (round 2 R1) |
| Relics nobody wears in `unwornRelics` | Every Relic is in `UserRelicData.Relics`; unworn means not in any Champion's `RelicIds` | Yes |
| Each Relic appears once | None is on two Champions on the Account read (live check) | Yes |
| `id`, `typeId`, `name`, rarity, level | `Id`, `TypeId`, `RelicType.Name`, `RelicType.Rarity`, `Level`, plus a `Rank` | Yes, plus `rank` (round 2 R4) |
| Stat bonuses in the Artifact bonus shape | Derived from type, level and static tables. No Glyphs, no rolls | Yes, worked out from the tables (round 2 R3), indexed by level (live check) |
| Passive effect as `typeId` and `name` | Skills: the type's, the Faction's, and each socketed stone's | Yes, as skills |
| Not foreseen | Relic stones in sockets | Yes: `sockets` on each Relic, and `unsocketedRelicStones` (round 2 R2) |

A Relic's `Rank` is not the glossary's Rank, which is a Champion's star count, so the glossary adds Relic rank, and Relic stone.

The maintainer settled the shape on 2026-11-10 (grill round 2, R1 to R5, every recommendation accepted), and https://github.com/ANicholasson/raid-bridge/issues/4 records it.
