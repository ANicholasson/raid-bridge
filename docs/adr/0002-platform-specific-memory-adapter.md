# Only the memory adapter is platform-specific

The Game client runs on Windows today, and under Wine or Proton on Linux. Development happens on Linux and macOS, and CI runs on Windows and Linux (amended 2026-11-01; macOS left out of CI on 2026-11-13). So the only platform-specific code is the memory adapter: the code that finds the Game client's process and reads its memory. Each platform gets its own adapter behind one port, starting with Linux (the Game client under Proton), and a fake implements the same port over a synthetic Game client the tests build (amended 2026-11-01). One contract test suite runs against all of them. Everything else (metadata parsing, mapping, the Snapshot model, the exporter) targets plain `net10.0` and builds and tests anywhere. Decided 2026-10-27, with Linux first since 2026-10-31.

## Considered Options

- **Windows first.** The game's supported platform, with a well-trodden read path and no permission step. Chosen at first, then replaced on 2026-10-31 (#9): the maintainer plays on Linux and would have had to reboot into Windows for every Snapshot, and the game plays normally under Proton with a read permission the player already has. A Windows adapter still comes later, behind the same port (amended 2026-11-09).
- **Target `net10.0-windows` throughout.** Simpler, with one platform and no port, but then nothing builds or tests off Windows, every development session needs a Windows machine, and a Linux or Mac reader would mean untangling Windows calls from the rest.

## Consequences

- Adding a platform means adding an adapter that passes the contract suite, with no change outside it. The Windows adapter (`RaidBridge.Game.Windows`, 2026-11-13) finds `Raid.exe` in the system's process list, opens it with `PROCESS_VM_READ` and `PROCESS_QUERY_LIMITED_INFORMATION` only, finds `GameAssembly.dll` as the module whose image exports under that name, reading the headers of each module `K32EnumProcessModulesEx` lists, takes its file from beside `Raid.exe` (`QueryFullProcessImageNameW`), and reads with `ReadProcessMemory`. It never asks Windows for a module's file, which Microsoft documents as needing `PROCESS_QUERY_INFORMATION` (https://github.com/ANicholasson/raid-bridge/pull/49). Unlike the Linux one, it holds a handle to the Game client, which a program inside the game could see; it never asks for more than reading. Linux can read a Wine or Proton process with `process_vm_readv`. Most distributions restrict that to child processes (`kernel.yama.ptrace_scope`), but Steam's container puts the game in a user namespace the player owns, so the player's own user may read it with no setup step (#13, amended 2026-11-01). A native Mac client, if one exists, is a different build and needs checking first.
- `tests/RaidBridge.Guardrails.Tests` lists each platform's write, attach and inject calls, and each new adapter extends it. The Linux adapter added `process_vm_writev`, `ptrace` and the rest of spec #20's list, and an allowlist of native imports (#24). The Windows adapter (2026-11-13) added its six kernel32 imports to that allowlist, and a check that the two rights an OpenProcess call may name carry their Win32 values.
- Reader logic is tested against the synthetic Game client (`tests/RaidBridge.Game.Testing`), never against a running Game client. The synthetic client can drift from the real one after a game update, so each adapter needs live checks against the running Game client. They run only when `RAIDBRIDGE_LIVE=1`, and once opted in, a missing Game client fails them rather than skipping them (amended 2026-11-01). <!-- (PR #56) -->
- CI runs the gate on Windows and Linux, so code outside the adapters stays portable (amended 2026-11-01). macOS ran it too until 2026-11-13, when it was turned off until raid-bridge supports macOS: its runners waited 10 to 15 minutes to start and PR runs were cancelled while waiting, so nothing checks that the code still builds there. A platform's adapter is tested there when it lands.
